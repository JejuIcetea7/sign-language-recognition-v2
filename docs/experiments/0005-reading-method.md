# 0005. 영상 읽기 방식 비교 (seek vs 순차 읽기)

실험 전에 작성한 계획이다. 결과는 아직 기록하지 않았다.


## 목적
24프레임 기준으로 두 읽기 방식을 비교하고, 메인 파이프라인에 쓸 방식을 정한다.

- **seek:** 프레임 번호마다 `cap.set(CAP_PROP_POS_FRAMES)`로 이동한 뒤 `cap.read()`로 읽는다. 현재 메인 방식이다.
  - 압축 영상은 키프레임이 아닌 프레임을 앞 프레임에 의존해 저장한다. 그래서 이동하면 목표 앞의 가장 가까운 키프레임으로 가서 목표 프레임까지 디코딩한다.
  - 프레임 번호마다 이 과정을 반복하므로, 같은 키프레임에서 시작하는 구간은 읽을 때마다 다시 디코딩한다.
  - 번호를 직접 지정해 읽는다. 이동 결과가 목표와 정확히 맞는지는 코덱과 영상에 따라 다를 수 있다.
- **순차 읽기:** 영상 앞에서부터 `cap.grab()`으로 한 프레임씩 넘기면서, 필요한 번호에서만 `cap.retrieve()`로 이미지를 꺼낸다.
  - `grab()`은 디코딩만 하고, `retrieve()`가 디코딩된 프레임을 이미지(BGR)로 변환한다. 필요 없는 프레임은 변환하지 않는다.
  - 영상을 한 번만 훑으므로 같은 프레임을 다시 디코딩하지 않고, 이동 과정이 없다.
  - 읽는 마지막 프레임까지 모든 프레임을 디코딩한다.
- 위 동작은 OpenCV의 FFmpeg 기반 구현에 대한 일반적인 설명이고, 이 실험에서 직접 확인하지는 않았다.

읽을 프레임 번호는 두 방식 모두 같다. (앞 3초를 24구간으로 균등 분할)

대상은 22개 단어에서 10개씩, 영상 220개이다. (단어별 파일 목록에서 균등 간격으로 선택)


## 1. 두 방식이 같은 프레임을 읽는가
- 영상마다 두 방식으로 24프레임을 읽어 이미지(픽셀)를 비교한다. (병렬 실행)
- 이미지가 다른 프레임은 MediaPipe 특징(111개)의 최대 절대 차이도 기록한다.

**결과** (원본: `outputs/reading_experiment/frame_compare.csv`)
- 프레임 5280개 중 5233개(99.1%)는 이미지가 같았고, 47개(0.9%)는 달랐다. 읽기 실패는 없다.
- 다른 프레임이 있는 영상은 5개(2.3%)이고, 모두 24프레임 중 12~23번째에 있다.
- 다른 프레임의 특징 최대 차이는 127.4(중앙값 16.9)이다.
- `person4_coke (2)`에서 seek의 48번 프레임이 순차 읽기의 47번 프레임과 같았다. (이 영상만 확인)


## 2. 읽기 시간
- 영상을 열어 24프레임을 읽는 시간만 잰다. (MediaPipe, 모델 제외)
- 영상마다 방식별로 4번 읽고, 첫 번째는 파일 캐시 영향을 빼려고 버린다. 읽는 순서는 영상마다 번갈아 바꾼다.
- 하나의 프로세스로 순서대로 측정한다.
- 기록: 방식별 읽기 시간의 p50, p95 (영상 220개 x 3회 = 660개 값)
