# 0008. 영상 읽기와 MediaPipe 처리 겹치기

실험 전에 작성한 계획이다. 결과는 아직 없다.  
현재 지연: [0006](0006-latency-24f-sequential.md) (영상 읽기 208 ms, MediaPipe 266 ms)


## 목적
영상을 읽는 동안 읽은 프레임을 바로 처리하도록 바꿔서, 특징 추출 시간이 얼마나 줄어드는지 확인한다.

- **현재:** 24프레임을 모두 읽은 뒤 MediaPipe로 처리한다. 걸리는 시간은 두 구간의 합이다.
- **겹치기:** 읽는 스레드가 필요한 프레임을 큐에 넣고, 메인 스레드가 큐에서 꺼내는 대로 MediaPipe로 처리한다. 프레임 순서는 큐가 유지한다. 큐 크기는 4로 제한해서 읽기가 처리보다 너무 앞서가지 않게 한다.

두 방식 모두 읽는 프레임과 계산하는 특징은 같다.


## 설정
- 비교 대상: 현재(순차), 겹치기
- 대상: 영상 220개 ([0005](0005-reading-method.md)와 같은 영상)
- 고정 조건: 24프레임, 순차 읽기, 해상도 1920x1080, GRU 모델


## 측정
1. **특징이 같은가:** 영상 220개에서 두 방식의 24프레임 특징이 완전히 같은지 비교한다.
2. **특징 추출 시간:** 영상을 열어서 특징을 얻을 때까지의 시간(읽기 + MediaPipe)을 p50, p95로 잰다. 영상마다 두 방식을 4번씩 실행하고 첫 번째는 버린다. 읽는 순서는 영상마다 번갈아 바꾸고, 하나의 프로세스로 순서대로 측정한다.
3. **엔드투엔드와 동시요청:** 겹치기를 서버에 적용한 뒤 [0006](0006-latency-24f-sequential.md)과 같은 방식으로 다시 잰다.


## 선택 기준
특징이 완전히 같고, 특징 추출 시간 p50이 10% 이상 줄면 메인 파이프라인에 적용한다.


## 결과
원본: `outputs/overlap_experiment/times.csv`

- 측정 1: 영상 220개 모두 두 방식의 특징이 완전히 같았다. (220/220)
- 측정 2: 특징 추출 시간 (영상 220개 x 3회 = 660개 값)

| 방식 | p50 | p95 |
|---|---|---|
| 현재(순차) | 496.5 ms | 550.9 ms |
| 겹치기 | 407.2 ms | 452.7 ms |

- 겹치기가 p50, p95 모두 약 18% 짧다. (선택 기준 10% 이상 충족, 메인 파이프라인에 적용)
- 측정 3: 서버 엔드투엔드와 동시요청 (적용 전은 [0006](0006-latency-24f-sequential.md))

**엔드투엔드 (p50 / p95, ms)**

| 적용 전 | 적용 후 |
|---|---|
| 486.3 / 538.6 | 418.0 / 456.3 |

**동시요청 (처리량 req/s, p50 / p95 ms)**

| 동시 접속 | 적용 전 | 적용 후 |
|---|---|---|
| 1 | 1.97, 508 / 517 | 2.15, 468 / 474 |
| 2 | 2.06, 965 / 1003 | 2.23, 897 / 952 |
| 4 | 2.15, 1844 / 1967 | 2.24, 1776 / 1912 |
| 8 | 2.10, 3783 / 3950 | 2.21, 3564 / 3872 |

- 엔드투엔드는 p50 약 14%, p95 약 15% 짧아졌다.
- 동시요청 처리량은 약 2.2 req/s로 5% 안팎 늘었고, 지연은 접속 수에 비례해 늘어난다.


## 한계
- 읽기와 MediaPipe가 각각 여러 코어를 쓰기 때문에 코어가 부족하면 겹쳐도 줄어드는 폭이 작아진다. 개발 맥(코어 11개)에서 측정하며, 홈서버에서는 달라질 수 있다.
